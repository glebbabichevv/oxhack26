## Problem Statement
Horizon works end to end (model, out-of-time backtest, live decisions, public site). A dashboard alone reads as "another screen": judges look at it, they do not take part in it. We need one moment the HRT judges and Tom 7 remember, built by the 02:00 freeze, without weakening the honesty that is our edge.

## What Makes This Cool
- **Time capsule:** tonight we seal our probabilities for every market that resolves before judging, with a hash we publish and timestamp before any outcome is known. On Sunday the judges watch the seal open and see the score, whatever it is. Theme TIME, literally; pre-registration, which quants respect.
- **Polymarket panel:** a judge opens a real Polymarket market and the side panel already says what Horizon thinks, with the interval, the edge after the spread, the call and when the edge is expected to be largest. Then (stretch) they ask the agent "why?" or "find me the edges in tomorrow's matches".

## Constraints
- Now ~15:50 Sat. Pivot window closes 20:00; feature freeze 02:00; Devpost by 11:30 Sun; judging 13:00–15:45 Sun.
- The extension is built on the existing Argos extension shell. The Argos **client layer** (`extension/src/background`, `content`, `kit`: everything that reads and acts on pages) is the reference and is **not modified**. Extension points used: (1) the agent gets Horizon through Argos's existing **custom MCP servers** feature (`integrations/mcp-servers`, added in the Integrations UI), so C needs no shell change at all; (2) the card is the one shell change: a new `HorizonCard` component mounted in `extension/src/panel/App.tsx` when the active tab is `polymarket.com/event/*`, on a private `lyto` branch `horizon`.
- The Argos shell stays in its private repo (`lyto`, branch for Horizon); only the Horizon module (formula, Gamma fetch, card UI, agent tool glue) goes in the public `oxhack26` repo. Devpost and the pitch say plainly: the shell is our existing product Argos; built here: the Horizon module, model and data.
- Zed / Delta track dropped; it is not an argument for anything.
- No faked numbers anywhere; the capsule result is shown whatever it is.

## Premises (agreed, with the user's corrections)

2. The model is 4 coefficients, so q can be computed in the browser. But the **decision** also needs: the domain (from the event's tags via Gamma; otherwise sports-only rules leak to other domains) and the spread (Gamma returns `spread`, `bestBid`, `bestAsk`, `endDate`, tags in one call). Verified 15:45: Gamma answers with `access-control-allow-origin: https://polymarket.com`, so a content script on polymarket.com can call it; the Argos background has `<all_urls>` anyway. No proxy needed.
3. The capsule is pre-registration, not proof. We write down **in advance what we expect**, so the outcome confirms or refutes a stated hypothesis instead of being read after the fact. Current test-set numbers (after the leak fix): sports, model beats market at 7d–12h (12h Brier 0.1802 vs 0.1819, 1d 0.1789 vs 0.1804), about equal at 30d (0.1109 vs 0.1106); crypto no lift; overall 0.1297 vs 0.1305. (The user recalled "model lost 0.1296 vs 0.1282" — that was the pre-fix run; corrected.) Expected ≤24 h gap is ~0.001 Brier on ≥1,705 markets, about one day's sampling noise; that is stated in the seal too. External timestamp: OpenTimestamps on the sealed file hash + the hash posted in the event Discord.
4. Replay duplicates the hero curve; lowest priority.
5. Pivot allowed until 20:00; after that only finishing; freeze 02:00.

## Approaches Considered
- **A. Card in the panel + Argos agent as is.** Good, but folds two risks together.
- **B. Card only.** ~1 h, no login or third parties. Guaranteed result.
- **C. Agent with a Horizon tool** ("go through tomorrow's matches and tell me where the edge is"). Strongest moment, highest risk (tool plumbing into the Argos agent).
- Replay / time-machine scrubber: deferred (duplicates the hero curve).

## Recommended Approach (chosen by the user)
Order: **capsule first** (first seal as early as possible), then **B** (card, ~1 h) as the guaranteed result, then **C on top**: the agent calls the *same* function that computes the card. **Hard deadline for C: 23:00.** If by then the agent does not pass the demo script reliably, the demo shows B and the agent is dropped.

### 1. Time capsule (Role A, start now)
- `backend/capsule.py`: fetch open binary markets (Gamma) that end before Sun 13:00 UTC, in the 3–97% band; for each record market id, question, domain, price_yes, spread, hours_to_resolution, q, q_low, q_high, action, at seal time. Write `capsule/seal-<UTC timestamp>.json` plus `capsule/EXPECTATIONS.md` (the pre-registered hypotheses below), compute SHA-256 of both, `ots stamp` the hash, commit, post the hash in Discord.
- **Sample (counted 15:55):** at least 1,705 open in-band binary markets end before Sun 13:00 UTC (Gamma's offset cap hit at 2,100 returned; the seal uses keyset pagination to get all). Every market in a seal is under ~19 h from its scheduled end, so the capsule tests **only the ≤24 h horizons**; it says nothing about 7d or 30d, and the seal file says so.
- **Pre-registered expectations (in `capsule/EXPECTATIONS.md`, committed before the first seal):** (a) all markets, ≤24 h: model Brier below market, test-set reference 1d 0.1275 vs 0.1285, 12h 0.1246 vs 0.1258 (gap ≈0.001); (b) sports ≤24 h: same direction, reference 1d 0.1789 vs 0.1804, 12h 0.1802 vs 0.1819; (c) crypto ≤24 h: no difference (reference 1d 0.0530 vs 0.0530); (d) a ~0.001 gap is about the size of one day's sampling noise at this n, so an inconclusive or reversed result is a likely outcome and will be reported as such, with a bootstrap CI by event; (e) P&L is not the metric.
- **Inclusion rule (pre-registered):** the seal's market list is fixed by a deterministic filter written in the script and in EXPECTATIONS.md (binary, active, 3–97%, scheduled end before Sun 13:00 UTC, one row per market). At opening, only markets with a final YES or NO resolution are scored; unresolved, disputed, cancelled, postponed and 50/50 markets are excluded and **their count is reported next to the score**. No other exclusions.
- **Two seals, scored separately (pre-registered):** Seal 1 (~19:00 Sat) is **primary**; Seal 2 (~01:30 Sun) is secondary. Both are always reported. Within a seal each market counts once; overlap between seals is expected and not merged.
- The seal file is committed and pushed to the public repo; one hash per seal is posted in Discord; the hash is stamped with OpenTimestamps. The claim is "pre-registered and timestamped", not "unforgeable".
- `backend/capsule_open.py` (Sunday): fetch outcomes, score Brier model vs market overall and on the pre-registered slices, write `capsule/open-<ts>.json`; `/api/capsule` serves it; the site gets a "Sealed at … · opened at …" section.

### 2. Card in the Argos panel (B)
- **One domain classifier for both sides:** the tag→domain map (`DOMAIN_TAGS` in `integrations/common.py`) is exported by `GET /api/model` together with the coefficients; the extension applies the same map to the Gamma event's tags. Parity is checked from the **raw Gamma event**, not from a pre-labelled domain.
- Horizon module: `horizon.ts` with `decide({price, hours, domain, spread})` → `{q, lo, hi, edge, net_edge, action, kelly}` using coefficients from `GET /api/model` (new endpoint exporting the fitted coefficients and the bootstrap coefficient sets, so the interval is exact, not approximate). Same decision rule as `backend/model.py` (band 3–97%, cost = max(spread/2, 0.01), robust rule, ¼ Kelly cap 5%).
- On `polymarket.com/event/*`: read the slug from the URL, call Gamma `/events?slug=`, show one card per binary market in the side panel: market price vs Horizon q with interval, the call, edge after spread, and "edge largest at 12h–1d" from the backtest's by_horizon.
- Parity check: for 20 raw Gamma events, the module's domain, q, interval, net edge and action equal the Python pipeline's for the same inputs (q to 1e-6).
- Card states: non-binary leg → hidden; outside 3–97% → NO_TRADE "outside the modelled band"; closed/resolved → hidden; missing spread → 1¢ floor, noted; Gamma or `/api/model` error, or >2 s → "Horizon unavailable, retry"; `/api/model` is cached in the extension with a bundled fallback copy. Reason strings reuse `/api/live`'s.

### 3. Agent with the Horizon tool (C, stop at 23:00)
- A small **Horizon MCP server** (HTTP, served next to the API) with two tools that run the Python pipeline (`backend/model.py` + `DOMAIN_TAGS`), the reference the TS module is parity-checked against: `horizon_check(slug)` and `horizon_scan(tag="sports", within_hours=24, top=5)` (open in-band markets with that tag ending within the window, ranked by net edge). Added to Argos via Integrations → MCP servers; no shell code changes. Demo script: open a match page → "should I buy?" → agent calls `horizon_check`, quotes the call, explains the bias in one sentence → "where else is there edge tonight?" → `horizon_scan`. Go/no-go at 23:00.

### R2-1 — consistency (minor)

**Problem**

> Premise 3 still says the expected Sunday gap is ~0.0015 Brier and that '~100 markets' cannot resolve it. The updated capsule section says the gap is ~0.001 and counts at least 1,705 markets. The two parts of the document now disagree on both the sample size and the gap.

**Remedy**

> Update Premise 3 to the counted sample (>=1,705) and the <=24h reference gap (~0.001), or point it to the capsule section.

### R2-2 — clarity (minor)

**Problem**

> The '<=18 h' bound looks off by about an hour. Seal 1 at ~19:00 Sat London time (BST, so 18:00 UTC) is about 19 h before the Sun 13:00 UTC cutoff. The '<=24 h' conclusion still holds. Separately, the capsule.py bullet says 'Sun 13:00 Europe/London' while the inclusion rule says 'Sun 13:00 UTC'. These are the same instant only because the clocks go back at 02:00, so the deterministic filter should name a single zone.

**Remedy**

> State the bound as '<=~19 h' or 'under 24 h'. Use 'Sun 13:00 UTC' everywhere, including in capsule.py and EXPECTATIONS.md.

### R2-3 — clarity (minor)

**Problem**

> decide() is defined as the TypeScript horizon.ts module, but the MCP server is Python, 'served next to the API'. It is unclear whether the MCP tools call the Python backend/model.py path or a port of the TS module. If the latter, it is also unclear whether the parity check covers it.

**Remedy**

> Say that the MCP tools use the Python pipeline (backend/model.py plus DOMAIN_TAGS), the reference the TS module is checked against for parity.

### R2-4 — completeness (minor)

**Problem**

> The card states cover Gamma failures, but not a failed or slow GET /api/model, which the card needs for its coefficients, bootstrap sets and domain map.

**Remedy**

> Either cache /api/model in the extension with a bundled fallback copy, or show the same 'Horizon unavailable, retry' state when it fails.

### R2-5 — feasibility (minor)

**Problem**

> Approach C depends on hosting an HTTP MCP server. Vercel's Python serverless functions may not support the streaming or long-lived connections some MCP transports need. This is listed as an open question and C has a 23:00 go/no-go, so the risk is contained, but it has no fallback host.

**Remedy**

> Name a fallback for the check: run the MCP server locally on the demo laptop (localhost), or use a stateless streamable-HTTP transport.
